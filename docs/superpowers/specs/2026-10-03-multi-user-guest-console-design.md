# T2VA 多用户与游客模式、控制台改版设计

**日期：** 2026-10-03  
**状态：** 已获用户确认（2026-10-03）  
**范围：** V0.1 后续迭代；Go/SQLite Cloud、Worker 任务闭环、现有 `web/index.html` 前端

## 1. 目标与确认过的产品决策

本设计落实已确认要求：

- 支持多用户注册与登录，暂不要求邮箱或手机验证。
- 支持游客模式，不强制游客先注册即可体验任务流程。
- 游客历史绑定服务端匿名会话及当前浏览器持有的会话凭证；清除浏览器数据后可能无法恢复。
- 游客任务不自动迁移或合并到注册账号。
- 注册用户只访问自己的任务、历史和结果；游客只访问自己匿名会话的资源。
- 重做控制台视觉与信息架构，提供现代化的生成工作区、任务历史、账号入口和明确的运行状态；不复制参考站点的品牌或专有素材。
- 开发过程留痕：重要决策、实现阶段、验证命令、结果、限制和待办记录到项目文档，避免记录密码、令牌等秘密。

## 2. 当前基线与关键差距

现有 Cloud 使用 Go、SQLite 和文件存储，任务记录有状态、提示词、输入/输出文件 ID 与时间戳。`web/index.html` 是当前唯一明确的前端入口。当前 API 的 `USER_API_KEY` 是可选全局 Bearer Key，不是账号体系；任务表没有用户/游客所有者字段，任务读取及结果下载尚未执行按主体隔离。前端改版必须依赖后端授权边界，不能用仅隐藏 UI 的方式实现“我的历史”。

## 3. 建议架构

### 身份与会话

- 新增 SQLite 用户实体：稳定 ID、规范化登录名、密码哈希、创建时间和必要的状态字段。暂不采集或要求验证邮箱/手机号。
- 密码只存专用 KDF 生成的哈希（优先 Argon2id，参数明确且可配置/审计）；绝不存明文或可逆密文。
- 使用服务端随机会话令牌，数据库只存令牌哈希、主体类型/ID、创建/过期时间；浏览器通过 `HttpOnly`、`SameSite` Cookie 持有凭证。生产环境要求 HTTPS 并设置 `Secure`；本地 HTTP 开发需明确的开发配置。
- 游客首次访问时创建匿名主体与会话。游客会话凭证不能由客户端选择任意主体 ID；退出或过期后按会话策略失效。
- 注册、登录、登出和游客会话入口使用一致的认证中间件；原 `USER_API_KEY` 仅可作为迁移期/运维兼容选项，默认不允许它绕过主体授权访问个人数据。
- 登录名规范、密码最小要求、登录错误响应和注册冲突响应在实现计划中具体化；任何认证接口须限速/防枚举属于上线前安全待办，V0.1 至少做请求体限制和统一错误响应。

### 任务与文件所有权

- 任务记录增加主体类型及主体 ID（或等效不可混淆的所有者键），新任务创建时由服务端身份上下文写入，不接受请求体覆盖。
- 用户历史 API 支持分页、稳定排序与状态筛选；单项详情与结果下载均先校验所有者。未授权资源返回与不存在相同的 404，避免泄漏 ID 是否有效。
- 文件也必须有所有者关联：输入文件上传属于当前主体；创建任务要求输入文件归当前主体；任务结果下载先校验任务所有权。Worker 内部下载/上传仍由独立 Worker Token 授权，不依赖浏览器会话。
- 历史列表返回必要展示字段，不暴露 worker 内部凭证或无关路径。删除历史/文件策略需与任务状态和存储清理保持一致；初版可不提供删除，避免误删运行中数据。
- 现有 SQLite 数据迁移采用可重复、向前兼容策略。旧数据不能归给任意新用户；实现时将旧任务标记为不可由普通主体访问的 legacy/system owner，并记录迁移规则。

### 前端控制台

- 不引入大型前端框架，先使用现有静态入口与浏览器原生 HTML/CSS/JS，除非检查后发现项目已有构建链。
- 响应式控制台：桌面侧栏/顶栏、清晰的主内容层级、生成面板、任务状态/结果区、历史列表、登录/注册入口、游客身份提示与账号资料区。
- 统一状态反馈：加载、空数据、上传错误、任务失败、网络断开及登录失效均可读、可键盘操作；危险或不可逆操作需确认。
- 适配窄屏、可见焦点、语义化控件和足够对比度。避免仅以颜色表达任务状态。
- 页面调用会话 API，不把会话令牌放入 localStorage/sessionStorage；游客模式的浏览器清理后历史不可恢复需在界面解释。

## 4. 核心数据流

1. 浏览器启动后检查会话；若无会话则请求创建游客会话，之后读取当前主体的历史。
2. 注册/登录成功后更新 HttpOnly Cookie；游客旧会话任务保持原主体，不自动转移。
3. 图片上传由服务端认证并绑定所有者；创建任务时再次验证输入文件所有权并绑定当前主体。
4. Worker 继续通过 Worker Token 获取被分派任务输入、上传输出并回报状态。
5. 浏览器只能按当前会话查询任务、历史与结果；每个 API 查询均在服务端带所有者条件。

## 5. 安全与可靠性约束

- Cookie 会话认证需防 CSRF（SameSite 与 Origin/CSRF token 策略），WebSocket Worker 认证与用户会话分离。
- 注册/登录均使用 TLS 部署；限制请求体与密码长度；密码哈希使用成熟库与安全参数；会话随机数使用 `crypto/rand`。
- 不向 API 返回密码哈希、会话令牌或 Worker Token；不把凭证写入开发日志。
- 所有文件和结果访问都做主体授权；路径 ID 校验继续保留，不能替代授权。
- SQLite 外键/索引、并发迁移和旧数据处理需有测试。
- 现有 Dispatcher 多任务同时分派问题是独立的高优先级可靠性问题：限定单 Worker 单活动任务、任务完成/失败/断线状态一致性，并补并发回归测试；作为本迭代安全上线前置项。

## 6. 测试与验收

- 单元/集成测试覆盖游客会话创建、注册/登录/登出、密码哈希不泄露、会话过期、用户与游客主体隔离、跨主体访问详情/文件/结果拒绝、历史分页、旧数据库迁移。
- 任务 API、Worker API 的授权边界相互独立；Worker 完成任务后仅任务所有者能查看输出。
- Dispatcher 测试证明单个 Worker 同时最多有一个活动任务，并验证完成、失败、断连重排队后可以继续分派。
- 前端至少做 HTML/JS 静态检查（若现有工具允许）、关键流程浏览器测试或可复现的 HTTP 流程；测试不可执行时记录原因，不把静态构建当端到端验证。
- 验收命令包括 `go test ./...`、`go vet ./...`、`go build ./cmd/cloud ./cmd/worker`；Docker 镜像构建和本地 Cloud/Worker 端到端运行单独记录。
- 验收必须包含用户隔离证明：用户 A 创建的任务/输入/结果对用户 B 与游客不可见；游客资源对注册用户不可见。

## 7. 分阶段实施

1. 身份、会话与数据库迁移设计定稿，确定密码哈希依赖和 Cookie/CSRF 方案。
2. 实现主体解析、游客会话及注册/登录/退出 API，并先添加认证测试。
3. 加入任务/文件 owner 数据迁移与服务端授权查询，增加跨主体回归测试。
4. 修复 Dispatcher 单活动任务约束，测试并发、完成、失败和断线恢复。
5. 改造静态控制台，接入会话、生成、状态轮询与隔离后的历史列表；完成响应式与可访问性检查。
6. 运行全量检查与本地闭环，记录未完成项、安全限制和部署说明。

## 8. 不在本次范围

- 邮箱/手机验证、密码重置、OAuth/SSO、组织/团队、角色管理与计费。
- 游客历史向账号迁移。
- 生产级反滥用、验证码、复杂审计后台；应在开放公网注册前补齐必要防护。
- 真正的 MiniMax H3/ComfyUI 视频生成工作流；现有 MockEngine 不能产生可播放视频。
- 多 Worker 调度、队列系统、Redis 或 Kubernetes。

## 9. 待实施阶段复核的决定

本设计沿用用户已确认的多用户、免邮箱/手机验证、游客模式及游客数据不迁移规则。实施前需复核现有静态部署与 Go 版本能否直接使用 Argon2id 依赖；若依赖下载或兼容性受限，先报告事实并提出等强度替代，不自行降级到快速哈希。公开注册虽按当前决策实现，但公网开放前仍需防滥用与运维策略。
